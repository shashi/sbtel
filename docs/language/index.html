The sbtel language

An sbtel spec is a text file of nested, parenthesised forms. There are ten forms and a few keywords, and this page shows each one with a small example. Core concepts explains why the language is shaped this way; the Reference has the exact rules.

#The forms

FormWhat it says
(block Name …)A part of the system: a feature, a service, a file, a function. It may hold levels of its own.
:type "…"What a block, behavior or shape is in code. Shown as a pill.
(sketch "…"), (~ … ~)One plain sentence about an element. The tilde form needs no quoting.
(level :name "…" …)One level of a block. Levels run top to bottom; each is built from the ones below. :name is the vocabulary it offers upward.
(adjacent …)Blocks in one level that may name each other, with a sketch that says why.
(takes T), (gives T)A value of shape T that a block takes or sends. The port is named after the type: noteSaved for NoteSaved.
(takes T :as name)The same port with a name of its own, for when the type’s name is not enough.
(shape Name …)A type of value that blocks exchange without naming each other.
(refines T)Inside a shape: is-a. A port that takes T takes this type too.
(carries A B)Inside a shape: has-a. A value of this type holds values of A and B.
(behavior Name …)An interface: a named set of ports and a sketch of what holds.
(implements Name)A block, or another behavior, takes on a behavior’s ports.

A ; starts a comment that runs to the end of the line. Names are any run of characters without spaces, parentheses, quotes or ;, so store.ts and Clock.Counter are fine.

#Blocks, :type and sketches

A block has a name, an optional :type right after it, and a sketch: one sentence about what it is for. Both sketch forms mean the same thing; (~ … ~) is easier to type because nothing inside it needs escaping.

#Levels

A block’s levels are written top to bottom, and the first is the top. A level’s sketch, when it has one, says what the level above may know of it.

Blocks written directly in a block, without a (level …) around them, form a level of their own. That is handy for a block with a single level.

#Adjacency

Blocks in a level are independent unless you say otherwise. adjacent says otherwise: these blocks know each other, and its sketch says why.

#Ports and shapes

A port is something a block takes (takes, on the card’s top ear) or gives (gives, on its bottom ear). What it takes or gives is a shape in scope. The name comes from the type, so most ports need nothing more. Write :as when a block has two ports of one type, or when a name says more than the type does. A sketch after the type adds what the type alone does not say.

#refines and carries

Two relations between shapes: refines for is-a and carries for has-a. Store takes Edit, so it takes RemoteEdit too. Core concepts has more on both.

#Behaviors and implements

A behavior is an interface: ports, a sketch, and a :type that says what it is in code (an interface, a trait, a protocol). A block that implements it gets its ports. A behavior can implement another behavior to extend it.

Shapes and behaviors are scoped: declared in a block, they can be used in that block and anything inside it. Declared at the top of the file, they can be used everywhere.

#Writing a spec, step by step

This is one way to write a spec from nothing, using the Notes app. Core concepts explains the reasons for each step.

#1. Name the bottom vocabulary first

Start with the parts everything else is said in: the ones that know nothing about the rest of the system. For Notes, that is storing notes, parsing Markdown and indexing words. Give each block a one-sentence sketch. If the sentence needs an “and”, it is probably two blocks.

step-1.sbtel
(block Notes
  (level :name "Stored notes"
    (block Store (~ Keeps notes on disk. ~))
    (block Markdown (~ Turns text into a document tree. ~))
    (block Index (~ Maps words to notes. ~))))

#2. Add levels above it

Ask what is written in terms of that vocabulary, and put it in a level above. Then do the same again. Name each level for what it offers upward: “Stored notes” is what Editor, Preview, Sync and Search are written in, and “Notes as text” is what Shell is written in.

step-2.sbtel
(block Notes
  (level :name "The app"
    (block Shell (~ Opens the window and wires the parts together. ~)))
  (level :name "Notes as text"
    (block Editor (~ The text area. ~))
    (block Preview (~ Renders the note beside the editor. ~))
    (block Sync (~ Exchanges edits with the cloud copy. ~))
    (block Search (~ Finds notes by their words. ~)))
  (level :name "Stored notes"
    (block Store (~ Keeps notes on disk. ~))
    (block Markdown (~ Turns text into a document tree. ~))
    (block Index (~ Maps words to notes. ~))))

#3. Declare shapes

Look for places where a lower block has to tell a higher one something, or where two peers exchange data. Each one is a shape with a gives on one side and a takes on the other. Here Store says when a note has been saved, and Editor and Sync listen.

step-3.sbtel
(block Notes
  (shape NoteSaved (~ A note reached the disk. ~))
  (level :name "The app"
    (block Shell (~ Opens the window and wires the parts together. ~)))
  (level :name "Notes as text"
    (block Editor (takes NoteSaved) (~ The text area. ~))
    (block Preview (~ Renders the note beside the editor. ~))
    (block Sync (takes NoteSaved) (~ Exchanges edits with the cloud copy. ~))
    (block Search (~ Finds notes by their words. ~)))
  (level :name "Stored notes"
    (block Store (gives NoteSaved) (~ Keeps notes on disk. ~))
    (block Markdown (~ Turns text into a document tree. ~))
    (block Index (~ Maps words to notes. ~))))

#4. Declare adjacency where two parts really are one unit

Sometimes two peers are one cooperation split for clarity. The preview scrolls with the editor line for line, and making them talk through ports would only hide that. Put them in an adjacent group and say why in its sketch. The coupling is then a decision anyone can see in the picture, and sbtel check allows it.

#5. Lint it, then check the code

Run sbtel lint after every edit. When there is code, list who names whom in an edges file and run sbtel check. With the shape and the adjacent pair in place, Store no longer names Editor, and the link from Preview to Editor is a coupling the spec declares:

output
$ cat edges.txt
Shell -> Editor        # src/shell.ts:12
Shell -> Preview       # src/shell.ts:13
Shell -> Sync          # src/shell.ts:14
Shell -> Search        # src/shell.ts:15
Editor -> Store        # src/editor.ts:40
Preview -> Markdown    # src/preview.ts:9
Preview -> Editor      # src/preview.ts:31
Sync -> Store          # src/sync.ts:22
Search -> Index        # src/search.ts:7
$ sbtel lint notes.sbtel
notes.sbtel: ok (9 blocks, 0 behaviors, 1 message type)
$ sbtel check notes.sbtel --bindings edges.txt
notes.sbtel: 9 bindings, 0 not allowed

An edge that still breaks the levels on purpose can be explained in place: a # VIOLATION: reason line right above it in the edges file. sbtel check still counts it, and prints the reason with it.

#The checks you will meet

sbtel lint reads the spec on its own. These are the reports you are most likely to see, in plain words.

An undeclared type
A port uses a shape that is not declared, or not in scope where the block is. Declare it, or fix the typo.
Out of scope
A shape or behavior is used outside the block that declares it. Move the declaration up to the smallest block that holds every use.
Two ports with one name
A block has two ports of the same type, so both got the same name. Give one or both a name with :as.
An unknown form
Usually a typo, such as skecth for sketch.
Placement notes
Information, never a failure: a declaration could live lower, closer to where it is used, or nothing uses it.
spec.sbtel, with problems
(block Notes
  (message Note (~ A title and a body. ~))
  (level
    (block Editor (port :in NoteSaved) (skecth "The text area."))
    (block Sync (port :in Note) (port :out Note))
    (block Search (port :in Words)))
  (level
    (block Store
      (message Words (~ The words of one note. ~))
      (port :out Note))))
sbtel lint spec.sbtel
spec.sbtel:5:33: warning: block Sync has two ports named note; tell them apart with :as
spec.sbtel:4:40: warning: unknown form (skecth) in block Editor
spec.sbtel: Every port uses a declared message type: Editor.noteSaved: NoteSaved
spec.sbtel: Message types are used only inside the block that declares them: Search.words uses Words, declared in Store
spec.sbtel: 4 problems (5 blocks, 0 behaviors, 2 message types)

sbtel check reads the spec together with the code’s edges. It allows an edge that goes down a level, stays inside a block, joins adjacent blocks, or calls through a behavior in scope. It reports three kinds of problem:

upward
A block names one in a higher level.
same-level
A block names a peer in its own level that is not adjacent to it.
ancestor
A part names the block that contains it.

The Reference lists every check with its exact message, and every rule of sbtel check.
