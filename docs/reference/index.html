The sbtel language

sbtel is a language to design, understand, and collaborate on a system's architecture with AI. A spec describes the system as nested blocks in ordered levels, the messages they exchange and the behaviors they share. This page describes the language exactly as core/core.js and core/api.js read it, for humans and agents alike. Every example on this page is checked against the sbtel binary (make docs-check): blocks marked clean lint clean, and every output shown is the binary's real output.

DESIGN.md is the contract for the tools (CLI, server, viewer). This page covers the language.

Rules in one breath.

  • Levels. Inside a block (or the file), levels run top to bottom. Higher levels are built from lower ones: a block may bind blocks in lower levels, never upward, and never a same-level block unless they are adjacent. A level's :name is a label for the vocabulary it offers upward.
  • Bindings (code in A names B) are allowed when B is: A itself, inside A, in a lower level of the nearest common holder (at any depth below it), or in A's adjacent group there. They are forbidden when B encloses A (ancestor), is in the same level but not adjacent (same-level), or is in a higher level (upward). B may also be a behavior: code that calls through an interface binds the behavior, not its implementers, and that is allowed when the behavior is in A's scope (abstraction).
  • Messages are data exchanged where neither side names the other: the counterpart is chosen elsewhere. Ports are typed with messages. accepts(U, T): an in U port takes an out T value when U = T or T refines U (transitively). carries (has-a) never changes what a port accepts.
  • Scope. A behavior or message type declared in block D is usable in D and everything inside D. Declared at file level, it is usable everywhere. Declare it where its users meet (lint notes it when it sits higher).
  • :type grounds a block, a behavior or a message type in code: what it is there (a module, a trait, a struct…). It shows as a pill. Keep the kinds consistent within a spec.
  • Names are any run of characters without whitespace, (, ), " or ;. Dots (Shell.Router) are a naming convention only. Duplicate block names get ids Name#2, Name#3… and a warning.

Checks (sbtel lint): parse errors; model warnings (duplicates, bad port direction, adjacent with fewer than 2 members, empty level, the old (layer …) and (either …)); structure warnings (unknown or misplaced forms and keywords, stray words, malformed ports, levels and carries, second sketches, blocks, levels and declarations inside a behavior…); six rules: every implemented behavior is declared, behaviors are used in scope, every port's type is declared, message types are used in scope, refines/carries name declared types, and no behavior implements itself; and placement notes (information, never a failure). sbtel check spec --bindings edges.txt applies the binding rules to Caller -> Callee # file:line edges.

The loop. Write the spec → sbtel lint spec.sbtel → fix → sbtel query spec.sbtel Id --with-deps to read just a slice → id=$(sbtel open spec.sbtel) for the human → sbtel inbox $id --wait (the human's review: a message, comments and a proposed spec) → apply or merge the proposal and edit → sbtel open spec.sbtel --session $id → sbtel reply $id c7.1 "done".

A complete, clean spec:

; A small notes app.
(block Notes
  :type "App"
  (sketch "Write notes, see them rendered, keep them on disk.")
  (message Edit (sketch "A change to one note's text."))
  (message Saved (sketch "A note was written to disk."))
  (behavior Durable
    (port edit in Edit)
    (sketch "Keeps every accepted edit until it is on disk."))

  (level :name "Editing"
    (adjacent (~ The preview scrolls with the editor. ~)
      (block Notes.Editor
        (port edit out Edit)
        (sketch "The text area where the user types."))
      (block Notes.Preview
        (sketch "Renders the note beside the editor."))))
  (level :name "Storage"
    (~ Editing sends Edits; it never touches files. ~)
    (block Notes.Store
      :type "Store"
      (implements Durable)
      (port saved out Saved)
      (sketch "Writes notes to disk and reloads them on launch."))))

#1. Lexical syntax

The reader turns text into four kinds of token:

  • Parens ( and ).
  • Tilde sketches (~ text ~), read exactly as (sketch "text") (§3.2).
  • Strings "…". A backslash takes the next character literally, so \" is a quote and \\ a backslash. There are no other escapes (\n is the letter n). A string may span lines.
  • Symbols: any run of characters that are not whitespace, (, ), " or ;. Names, keywords (:type) and port directions are symbols. Unicode letters are fine.

A ; outside a string starts a comment that runs to the end of the line. Whitespace is anything JavaScript's \s matches, including Unicode spaces.

The tilde sketch. ( followed directly by a run of k tildes opens one; the text runs to the first k tildes followed by ). Nothing inside is special: quotes, ;, #, backslashes, unbalanced parens, (~5 ms) and ~/.sbtel/ are all text. For a text that contains ~), use more tildes on both ends: (~~ … ~~) ends only at ~~), (~~~ … ~~~) only at ~~~), and so on. The tilde run is as long as it goes, so put a space after it: (~ ~) is the empty sketch. An opener with no closer is a parse error at the opener (§7.1).

Every form is a parenthesised list whose first item is a symbol naming the form. The ten forms are block, level, adjacent, port, message, refines, carries, behavior, implements and sketch. Anything else is reported by lint (§7.3) and otherwise ignored. 0.2 renamed layer to level and removed either; both are reported with what to write instead (§7.2).

Positions in messages are line:col, both 1-based; col counts UTF-16 code units, so for ASCII it is the byte column.

#2. The file

A file is a sequence of top-level forms: block, level, adjacent, message and behavior. The file behaves as an unnamed root block:

  • top-level blocks are laid out in the file's levels, exactly as children are inside a block (bare top-level blocks form an implicit level, §3.3);
  • top-level message and behavior declarations are in scope everywhere;
  • in binding messages the file is called "the file" (level 1 of the file).

Most specs have one top-level block. Several are fine:

(message Request (sketch "An HTTP request."))
(level
  (block Frontend (port call out Request) (sketch "The browser app.")))
(level
  (block Backend (port serve in Request) (sketch "The API server.")))

#3. Forms

#3.1 block

(block Name [:type "T"] body…)

A block is a part of the system. Name is its id; ids must be unique (a duplicate gets the id Name#2 and a warning). The body holds, in any order: sketch, port, implements, message, behavior, level, adjacent and block.

:type "Kind" is a block's one keyword, right after the name. It says what kind of code artifact the block maps to ("Service", "Module", "File", "Function"…) and shows as a pill in the viewer. Keep the kinds consistent within a spec, so the pills mean something. The value may be a string or a symbol. Any other keyword (0.1's :fill included), or a keyword after the body has started, is a warning; the viewer picks its own colours. Behaviors (§3.7) and message types (§3.6) take :type the same way, with the same warnings: a block says which code artifact it is, a behavior which abstraction ("trait", "interface", "Protocol", "typeclass"), a message type which data shape ("struct", "record", "protobuf message", "JSON schema"). It is optional: write it where it helps a reader find the thing in the code.

A block that contains levels is a container; its children are its parts. A block with no levels is a leaf.

#3.2 sketch

(sketch "What this element is for, in a sentence.")
(~ The same, as a tilde sketch: no quoting, no escapes. ~)

The prose description of a block, message, behavior, level, adjacent group or port. The two forms are equal in every respect but whitespace:

  • (sketch "…"): every run of whitespace is one space, so the text is one paragraph.
  • (~ … ~): the text is trimmed, and every run of whitespace is one space, except a run that holds two or more line breaks (a blank line): that is one paragraph break. \r\n and \r count as one line break. So a long tilde sketch can have paragraphs; the viewer shows them.

Only the first sketch of an element counts (a second one, in either form, is a warning). Neither form needs the other: write whichever reads better. Say one thing, in as few words as it takes; see the sbtel-design skill.

(message Path (~ A file path, like ~/.sbtel/sessions or "C:\Temp" (quotes and all). ~))
(message Note (~~ Ends with ~) inside, so it takes two tildes. ~~))
(message Long (~
  First paragraph.

  Second paragraph. ~))

#3.3 level and the implicit level

(level [:name "Name"] [sketch] block-or-adjacent…)

A block's (or the file's) levels are ordered top to bottom in source order. Higher levels are built from lower ones: the first level is the top. A level holds blocks and adjacent groups (and its sketch) only, and needs at least one block.

:name "…" labels the level: a string that is never referenced, may contain spaces and need not be unique. Name a level for the vocabulary it offers to the levels above it. A level's sketch states its abstraction barrier: what the level above may know of it, and what not. The viewer draws the name at the left of the line above the level. An implicit level has no name; write (level …) to give it one.

(block Rationals
  (level :name "Programs that use rationals"
    (block Calc))
  (level :name "Rational numbers as pairs"
    (~ Above here, a rational is make-rat, numer and denom; never the pair. ~)
    (block Rat)))

Bare block and adjacent forms written directly in a block form an implicit level. Consecutive bare forms share one implicit level, and an explicit (level …) ends the run. So this block has three levels, top to bottom [A B], [C], [D]:

(block Top
  (block A)
  (block B)
  (level (block C))
  (block D))

Levels do not nest directly: a level's members are blocks, and each block has its own levels.

#3.4 adjacent

(adjacent block-or-adjacent…)

An adjacent group is a set of peers in one level that may bind each other (§5). It needs at least two members. A nested adjacent is flattened into its parent group, so (adjacent (block A) (adjacent (block B) (block C))) is one group of A, B and C. A group may have a sketch, first or anywhere among its members: say why the peers are braided, in a few words. A nested group has no sketch of its own (lint warns); the outermost group's counts.

In the viewer, adjacent blocks sit side by side joined by a line.

#3.5 port

(port name in Type [sketch])
(port name out Type [sketch])

A typed input or output of a block or a behavior. Type names a message type in scope (§4), or, in a behavior with parameters, one of its parameters. Port names are unique within their block or behavior. After the type, a port may have one sketch: write it only when the type alone does not say what the port promises ((port chord in KeyChord (~ Opens the palette. ~))).

A block's ports are its own ports followed by the ports of every behavior it implements, sketches included.

#3.6 message, refines, carries

(message Name [:type "T"] [sketch] [(refines Super)] [(carries A B …)])

A message type is a kind of data. Two relations between types, and only these two:

  • is-a: (refines Super) makes Name a subtype of Super: a port that takes Super also takes Name. A union is a supertype that each alternative refines (0.1's either is gone).
  • has-a: (carries A B …) says a value of Name holds values of A, B…: types only, no field names or counts (the sketch says those). A subtype carries what its supertype carries. Recursion and cycles are fine (a Turn may carry Turns). carries never changes what a port accepts.

Each names declared message types; a carried type must be in scope where the message is declared, as a port's type must be (§4). :type says what the data is in code (§3.1): (message Edit :type "struct"). Only the first refines and the first carries count; a name twice in one carries is a warning.

(message Event (sketch "Something the user did."))
(message Click (refines Event))
(message Key (refines Event))
(message Selection (sketch "The selected ids."))
(message Camera (sketch "Pan and zoom."))
(message Snapshot (carries Selection Camera) (~ What undo restores. ~))

Who carries a type, transitively, and which ports and blocks use those carriers, is the core's carriers: sbtel query spec msg:Camera prints it under the type, and hovering a type in the viewer outlines them.

#3.7 behavior and implements

(behavior Name [:type "T"] (port …)… [(implements Other)…] [(sketch "…")])
(behavior (Name Param …) (port p in Param)… [(sketch "…")])
(implements Name)
(implements (Name Arg …))

A behavior is a named promise: a set of ports plus a sketch of what holds when a block has them. A block that implements it gains its ports. Several blocks implementing the same behavior share that vocabulary. A behavior is read with a block's grammar, keeping what has a meaning for a promise: the name, :type (what the abstraction is in code: a trait, an interface, a Protocol…; §3.1), a sketch, ports and implements.

Extension. (implements Other) inside a behavior extends Other, as a Rust supertrait, Java's interface A extends B or a protocol built on another do. The behavior has Other's ports too, and a block that implements it counts as implementing Other, transitively, everywhere "implementers of" matters: scope, placement notes, the viewer's outline and port partners. Other must be in scope where the behavior is declared (§4). A behavior that implements itself, through any chain (A implements B implements A), fails the rule "No behavior implements itself" (§7.4).

Parameters. A behavior may take parameters, written (Name P …). A port typed with a parameter is not checked against declared message types. (implements Name) leaves the parameters as they are (the ports keep the parameter as their type). (implements (Name Arg …)) passes one argument per parameter, in order: each port typed with a parameter takes the argument's type, in the ports the implementer gets. An argument is a message type in scope, or, inside a behavior with parameters, one of its own parameters, which its own implementer's argument replaces in turn: (behavior (Cache K) (implements (Store K))) and (implements (Cache Entry)) give Store's ports the type Entry. Arguments must fill every parameter (a warning otherwise).

What a behavior does not contain. Blocks, levels, adjacent groups, message types and behaviors are not allowed inside a behavior; each is a warning at its position, behaviors don't contain blocks, levels or declarations; declare … beside the behavior instead, and is left out of the model.

(message Event :type "struct" (sketch "One state change."))
(behavior (Store T) :type "trait"
  (port put in T)
  (port get out T)
  (sketch "Keeps values of T and returns them on request."))
(behavior Durable :type "trait"
  (implements (Store Event))
  (sketch "A Store of events that keeps every accepted one until it is acknowledged."))
(block Log
  (implements Durable)
  (sketch "An append-only event log."))

Log has the ports put in Event and get out Event (from Store, through Durable), and implements both Durable and Store.

#4. Scope

Behaviors and message types are scoped. A declaration inside block D is visible in D and in every block nested in D, at any depth. A declaration at file level is visible everywhere.

  • A block may implement only behaviors in its scope; a behavior, only those in scope where it is declared. The message types passed as arguments ((implements (Store Event))) follow the same rule.
  • A block's ports may use only message types in its scope.
  • A behavior's ports may use only message types in scope where the behavior is declared (not where it is implemented).
  • A message type may carry only message types in scope where it is declared.
  • Code may bind a behavior only where the behavior is in scope (§8, the abstraction rule).

Scope follows nesting, not levels: a message type declared in a block is visible to all of its children in every level, and to none of its siblings.

(block App
  (message Order (sketch "A customer's order."))
  (level
    (block App.Checkout
      (message CardToken (sketch "Opaque payment token; never leaves Checkout."))
      (port order out Order)
      (level
        (block App.Checkout.Form (port token out CardToken)))
      (level
        (block App.Checkout.Gateway (port token in CardToken)))))
  (level
    (block App.Fulfilment (port order in Order))))

Declare a type in the smallest block that holds every use of it. Declaring everything at the top works, but it hides which parts of the system share which data; lint notes each declaration that could live lower (§7.5).

#5. Levels and adjacency

Levels are the main idea. Read each block as a small stratified design: each level is a language built from the levels below it, and the boundary between levels is an abstraction barrier.

  • Order. Inside one holder (a block, or the file), levels are written top to bottom, and each level is built from the ones below it. Levels are numbered from the bottom: level 1 is the lowest. Code in level i may use level j only when j < i: a lower level has a lower number, as in "low-level". Lower levels know nothing of higher ones.
  • Same level. Blocks in the same level are independent of each other, unless they are adjacent.
  • Names and sketches. A level's :name is the vocabulary it offers upward ("Rational numbers as pairs"); its sketch, when the name does not already say it, is the barrier: what the level above may know of it. Binding messages name both: level 2 "Routing" of Shell.
  • Adjacency is a declared coupling: an explicit, visible statement that these peers know each other concretely. Use it when two peers really are one cooperation split for clarity (an editor and its live preview). Use it sparingly; it is a braid you chose, not a way around the levels. Its sketch says why, in a few words.
  • Depth. The rule is applied at the nearest common holder of the two blocks. A block deep inside level 2 may bind a block deep inside level 1 of the same holder.

#6. Messages, bindings and accepts

There are two ways for parts to depend on each other:

  • A binding is when code in block A names block B: it imports, calls, references or constructs it. Bindings must follow the levels (§8).
  • A message is data exchanged where neither side names the other: A has an out port, B has an in port, and the counterpart is chosen elsewhere (by a higher level, a router, configuration, a bus). Messages are how levels and peers talk without binding.

Ports are typed with message types, and accepts(U, T) decides whether an in U port can receive from an out T port:

  1. U and T are the same type; or
  2. T refines U, directly or through a chain (DoubleClick refines Click refines Event).

carries plays no part: a port that takes a Snapshot does not take the Camera inside it. With the types of §3.6 (and DoubleClick refining Click):

Lint does not require every port to be connected. accepts drives the viewer (selecting a port highlights every block that can talk to it) and sbtel diff's affected ports.

#7. Lint: every check

sbtel lint spec.sbtel reports, in this order: warnings with positions (file:line:col: warning: …), then rule failures (file: <rule>: <failure>), then placement notes (file:line:col: info: …, §7.5), then a summary line. A parse error stops everything and prints one line. The exit code is 1 when a warning, a failure or a parse error is reported; notes never change it. Below, every check with a minimal failing spec and its exact output (the file is called spec.sbtel).

#7.5 Placement notes

A message type or behavior belongs in the lowest block that holds all its users (the lowest common ancestor; the file counts, as the top). Lint notes a declaration that sits higher than that, or that nothing uses. Notes are information: they are not problems, never change the exit code, and the viewer shows them in the checks popover, muted, with a "Move to …" that makes the move (one undo step). Lint never suggests moving below the common ancestor: that is a scope failure.

  • Users of a message type T: blocks with a port of type T (inherited from behaviors too); blocks with a port of a type that carries T (transitively) or refines T; and the places that must see T: where each such type, and each behavior with a port of one of them, is declared.
  • Users of a behavior: the blocks that implement it, directly or through behaviors that extend it, and the places where each behavior that implements it directly is declared (it must be visible there). Lint does not read bindings, so a behavior that code calls through (§8) and that is declared where its callers can see it may still get a note that it could live lower, beside its implementers: keep it where the callers see it, and say why in a ; comment.
(message Deep (sketch "Carried by Note at the top: it must stay where Note can see it."))
(message Note (carries Deep))
(message Unused)
(block Shell
  (message Selection (sketch "Only Shell.View uses it."))
  (level (block Shell.View (port sel in Selection)))
  (level (block Shell.Log (port n in Note))))
(block Other (port n out Note))
output
spec.sbtel:3:1: info: Unused is never used.
spec.sbtel:5:3: info: Selection is declared in Shell but only used within Shell.View; it could live there.
spec.sbtel: ok (4 blocks, 0 behaviors, 4 message types)

--json gives each note as {severity: "info", message, line, col, kind, name, in, home}, where home is the block id it could move to ("" for the file) or null when nothing uses it.

#8. Bindings and sbtel check

A bindings file lists who names whom in the code, one edge per line:

Caller -> Callee            # optional location, e.g. src/caller.ts:12
  • Caller is a block id. Callee is a block id or a behavior's name (beh:Name names the behavior explicitly). Spaces around -> are optional; A->B is fine.
  • Everything after the first # that follows whitespace is the location, free text. Put the file and line there: a reviewer needs it to judge the edge.
  • Blank lines and lines whose first non-blank character is # are ignored. Any other line that is not exactly one edge (A -> B -> C, prose) is an error.
  • A comment line # VIOLATION: reason directly above an edge is that edge's explanation: why the code breaks the levels there. Comment lines after it, up to the edge, continue the reason (joined with spaces); a blank line, another # VIOLATION:, a line that is not an edge or the end of the file ends it without explaining anything. sbtel check still counts the edge, prints the reason under it and counts the explained violations; the viewer (sbtel open --bindings) shows the reason beside it. A note that explains no edge, or sits on an allowed edge, is a warning: it is stale or misplaced.
# VIOLATION: the store refreshes the UI itself; it should emit Changed.
Notes.Store -> Notes.Editor # src/store.ts:40

sbtel check spec.sbtel --bindings edges.txt judges every edge with the rule below. Let c be the nearest common holder of A and B (a block, or the file), and a2, b2 the children of c on the way to A and B.

ruleallowedwhen
sameyesA is B
descendantyesB is inside A, at any depth
lower-levelyesa2's level is above b2's level in c
adjacentyesa2 and b2 are in the same adjacent group
ancestornoA is inside B: a part may not bind the block that encloses it
same-levelnoa2 and b2 share a level of c but are not adjacent
upwardnoa2's level is below b2's
abstractionyesB is a behavior in A's scope: declared in A, in an ancestor of A, or in the file
scopenoB is a behavior declared outside A's scope
unknownnoA is not a block, B is neither a block nor a behavior (message types are neither), or a block is not placed in a level

Calls through an abstraction. When code in A calls through an interface, trait or protocol that a behavior stands for, the binding is A -> Behavior, not A to whichever block implements it: A names the abstraction only. The composition root, the code that builds the implementer and hands it to A, binds the implementer. That is dependency inversion, and abstraction makes it checkable: A may bind the behavior wherever its scope reaches, whatever level the implementers sit in. A block and a behavior may share a name (they are separate namespaces): a bare name binds the block, with a warning, and beh:Name binds the behavior. An unknown name gets a "did you mean" over blocks and behaviors.

#9. Annotations

Annotations tie code to spec elements, so that a tool or an agent can extract the bindings between blocks. An annotation is the token @sbtel inside a line comment, in any language (//, #, --, ;, %, ', <!-- … -->, or /* … */ on one line). There are four ownership forms and two anchors, and no others:

FormMeaning
@sbtel Namethe next declaration (function, class, type, constant…) belongs to block Name, or to behavior Name when it is an interface, trait, protocol or typedef that the behavior stands for (beh:Name when a block has that name too). One per declaration: a second one before the same declaration is an error
@sbtel begin Name … @sbtel end Namethe region between belongs to Name. Regions nest; the innermost wins. The end name must match its begin
@sbtel file Namefrom here to the end of the file belongs to Name
@sbtel message Nameanchor: where message type Name's shape is defined in code. It owns no code
@sbtel port Block.portanchor: where port port of block Block is handled. It owns no code

An anchor changes no ownership: the lines after it belong to whoever owned them anyway, and an @sbtel Name directly above an anchor still applies to the declaration below it.

// @sbtel file Shell.Router
import { notify } from '../notices.js';

// @sbtel Shell.Keymap
export function chord(event) { /* … */ }

// @sbtel begin Shell.Clipboard
function copy(text) { /* … */ }
function paste() { /* … */ }
// @sbtel end Shell.Clipboard

// @sbtel Shell.Router
// @sbtel message Intent
// @sbtel port Shell.Router.intent
export function route(intent) { /* … */ }
# @sbtel file Billing.Invoices
<!-- @sbtel file App.Page -->
//go:build linux

// @sbtel file Server.Detach

// Package server runs the shared localhost server.
package server

In Go, @sbtel file goes before the package clause (after any //go:build line), with a blank line between it and the package doc comment so that godoc does not include it.

Each of these names a leaf block (here, the leaf blocks Billing.Invoices and App.Page): @sbtel file with a container's name would make the whole file container code, which is an error (below).

Names use the spec's name syntax. An annotation checker reports: an unknown block name, or an anchor's unknown message type or port; an end without a begin or with a different name; a begin never ended; code in no block; code owned only by a container block (one with child levels), since code belongs to leaves; and a second @sbtel Name before one declaration, or a second @sbtel file in one file. Anything else after @sbtel is an error too: there is no long form. An @sbtel inside a string literal is not an annotation, and a multi-line string literal stays in its declaration. The sbtel-recover skill's sbtel_owners.py is such a checker.

To extract bindings, find every reference in code owned by block A to a declaration owned by block B (A ≠ B), and write A -> B # file:line for each. A reference to a declaration owned by a behavior X is A -> X (a call through the abstraction, §8), except one that states that A implements X (impl Durable for Store, class Store implements Durable, Go's var _ Durable = (*Store)(nil)): that is an implements relation, not a binding, and the spec should say (implements X) in A. The code of a behavior's own declaration binds nothing: its signature is the behavior's ports. Extraction is per language and lives outside the binary: the sbtel-recover skill (extracting-bindings.md) has the recipes, with or without an import graph, and helper scripts. A # VIOLATION: reason comment line directly above an edge explains why the code breaks the levels there; sbtel check prints it under the violation and sbtel open --bindings shows it beside it (§8). DESIGN.md §8 is the contract for the annotation forms.
