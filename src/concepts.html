Core concepts

sbtel rests on three ideas: a system is built in levels, a block can stand for any part of it, and levels connect through ports. This page explains each one with the small Notes app from the home page. Every diagram here is the real viewer: click one to use it, or ↗ to open it in the playground.

Stratified design

Stratified design is a simple concept that applies to any level of a system. A low level builds the language in which a higher level is written.

You already do this

When you explain a card game to a friend, you first define a few terms: a trick, a trump, the lead. Then you explain the rules in those terms. You never explain what a trump is in terms of the scoring.

Code is written the same way. You write a few helpers, such as parsing a date or escaping HTML. You write the domain in terms of them: save a note, render a note. Then you write the app in terms of the domain. Each layer is a small language, and the one above it is written in it.

Reading code works the same way, in reverse. In a new codebase you learn the vocabulary from the bottom up: what a Note is, what store.save promises. After that, the screens read like sentences.

When it goes wrong

Most people know the symptoms before they know the name for them:

  • Circular imports. The store imports the editor to refresh it after a save, and the editor imports the store to save. Neither can be understood, tested or replaced on its own.
  • A utils module that imports app code. It was meant to be the bottom of the system. Now nothing can use it without pulling in the whole app.
  • “I changed one thing and five broke.” Parts reached past each other’s vocabulary and into their insides, so a change that should have stayed local travels everywhere.

Each of these is a dependency pointing the wrong way: a lower part that knows about a higher one, or two peers that know each other without anyone deciding they should.

Levels

The fix is to write the levels down. In sbtel a block holds levels, written top to bottom. Each level is named for the vocabulary it offers to the levels above it. Code in one level may use anything in a lower level, and nothing in a higher one. Blocks in the same level are independent of each other.

Point at a level’s name to read what it offers, or at a block to read its sketch.

Once the levels are written down, a wrong dependency is something a tool can find. List who names whom in the code, one edge per line, and sbtel check reports every edge that goes up a level or sideways between peers:

Store refreshes the editor after a save, and Preview reaches into Editor, a peer it was never declared to know. The first is fixed with a port, as the rest of this page shows. The second may be a coupling you want: The sbtel language shows how to declare it.

The idea is old. Structure and Interpretation of Computer Programs draws a package for rational numbers as levels separated by abstraction barriers, and later calls the approach stratified design: a complex system structured as a sequence of levels, each described in its own language.

Generic blocks

Blocks are stand-ins for any kind of thing: a feature, a service, a file, a function. The rules about levels are the same for all of them, so you can describe a product by its features or a module by its functions in the same language.

:type grounds a block in code. It says what the block is there ("module", "service", "file"), and the viewer shows it as a pill. Keep the kinds consistent within a spec, so a pill means the same thing everywhere.

Blocks contain levels. That lets you expand a design progressively, for example with an AI agent: start with a subsystem, ask for one block to be opened into its parts, and go on down to a function. Here Store is a module, the module is two files, and one file is three functions. The same level rule applies inside each block.

Levels connect through ports

Store has to tell the editor when a note reaches the disk, but Store is in a lower level and may not name Editor. This is where ports come in.

Ports define interfaces by the shapes of the values that get passed around. A block declares what it gives with (gives T) and what it takes with (takes T), where T is a shape. Two ports fit when their shapes match, like the tab and the blank of two jigsaw pieces:

Click Store’s lower ear to open its outputs, then point at noteSaved: Editor lights up, because it takes that type.

Store has (gives NoteSaved) and Editor has (takes NoteSaved). Neither names the other. A port’s name defaults to its type’s name with a lowercase first letter, so these ports are both called noteSaved.

A port is not a wire

A pair of matching ports does not mean there is a communication channel in the sense of a wire. A wire itself would be a block in sbtel: a queue, a bus or a socket is a part of the system, with its own place in a level.

What matching ports denote is independence of existence. One block gives NoteSaved, another takes NoteSaved, and either could exist without the other. How the value gets from one to the other is implementation, not architecture: a callback, an event emitter, a channel, Elixir’s send and receive. In TypeScript, a callback might do it:

store.ts and shell.ts
// store.ts: knows nothing of the editor
export function save(note: Note, onSaved: (s: NoteSaved) => void) {
  write(note);
  onSaved({ id: note.id, at: Date.now() });
}

// shell.ts: the one place that knows both
store.save(note, saved => editor.markSaved(saved));

The callback is one way to build the wire, so there is no Callback type to model. The value it carries is the shape. If a callback returns something the lower part goes on to use, such as a conflict handler that returns the version to keep, that is a second shape flowing back: a gives on the higher block and a takes on the lower one.

Data shapes: refines and carries

Shapes have two relations, and only two. (refines Edit) is is-a: a RemoteEdit is an Edit, so a port that takes edits also takes remote edits. (carries Note) is has-a: a NoteSaved holds a Note. It never changes what a port takes, but it lets you follow one piece of data through the whole system.

Point at the Note type in the band at the bottom: every type that carries it lights up, and so does every block that sends or takes one.

Interfaces

Protocols, traits, abstract types, Java interfaces and Elixir behaviours all map to one form, behavior. Its :type says which one it is in your code.

  • Declare it where both sides can see it: in the nearest block that contains both the caller and the implementers. Lint’s placement notes point out a declaration that sits higher than it needs to.
  • The caller binds only the behavior. Code that calls through an interface names the interface, not whatever implements it. sbtel check allows that edge under its abstraction rule, wherever the behavior is in scope, whatever level its implementers sit in.
  • Implementers say (implements Repo) and gain the behavior’s ports.
  • Whoever wires them sits above both and binds both: the composition root, a supervisor, a configuration file.

Here Editor saves through Repo, DiskStore and MemoryStore implement it, and Shell builds a store and hands it to the editor:

Point at Repo in the band at the bottom: its implementers are outlined. Open DiskStore’s ears: its ports came from Repo.

This covers both directions an interface can point. A higher level can define an interface that a lower one implements, as with this Repo, which the domain needs and storage provides. And a lower level can define one that a higher level implements: a plugin host that calls the plugins it is given, or a framework that calls your code.

An abstract class that holds shared code as well as abstract methods is two things braided together. Split it into a behavior, for the abstract methods, and a block in a lower level that holds the shared code:

An example in Elixir

A higher level may slot into a lower level through an interface. GenServer defines a behaviour; your module implements its callbacks; the OTP loop calls yours without ever naming it. Elixir processes that message each other are sbtel messages, and they can sit on the same level, because neither names the other.

lib/clock/counter.ex
defmodule Clock.Counter do
  use GenServer                                   # (implements GenServer)

  def start_link(_), do: GenServer.start_link(__MODULE__, 0, name: __MODULE__)
  def init(n), do: {:ok, n}
  def handle_info(:tick, n), do: {:noreply, n + 1} # (takes Tick)
end
Point at GenServer in the band: both processes implement it. Open Clock.Ticker’s lower ear and point at tick: Clock.Counter, beside it, takes it.

gen_server -> GenServer is the loop calling back into your modules through the behaviour, which abstraction allows. The application is the supervisor that starts both processes and hands the ticker the counter’s name, so it binds both.

Rule of thumb. Callbacks are ports, interfaces are behaviors. Either way, the lower code never names the higher.
