Guide

sbtel describes a system as blocks in levels. This guide is the concept and the manual in one: each idea comes with the real viewer, live, so you can poke at it. Click a diagram to interact with it; ↗ opens it in the playground. Exact rules live in the Reference.

The kind of design sbtel helps you make

Architecture is mostly a question of what knows what. sbtel asks you to make four things explicit.

Levels are vocabularies.
As in the stratified design of Structure and Interpretation of Computer Programs, each level is a language built from the levels below it. A block may use what is below it, never what is above, so a lower level can change without the upper ones noticing.
One strand per block.
If a block's one sentence needs an “and”, it is two blocks. Simple, in Rich Hickey's sense (“Simple Made Easy”), means one strand, not braided with others.
Coupling is declared.
Peers in a level don't know each other unless you say they are adjacent: a braid you chose, drawn as a line. Anything else talks through messages.
Data is values.
A message is typed data that crosses a boundary, not a call. carries says what is inside it, so you can follow one piece of data through the whole system.
A notes app. Point at the line between Editor and Preview, at a level’s name, or at a dot on an ear. Click one to edit it.

The forms at a glance

That is the whole language: eleven forms and one keyword.

(block Name …)
A part of the system: a feature, a service, a package, a file, a function.
:type "…"
What a block, behavior or message is in code. It shows as a pill.
(sketch "…"), (~ … ~)
One plain sentence about an element. The tilde form needs no quoting.
(level :name "…" …)
One level. Levels run top to bottom; each is built from those below.
(adjacent …)
Peers in one level that may know each other.
(port name in|out Type)
A typed input, on the card’s top ear, or output, on its bottom ear.
(message Name …)
A kind of data, exchanged where neither side names the other.
(refines T)
Is-a: a subtype of T. A port that takes T takes it too.
(carries A B)
Has-a: a value of this type holds values of A and B.
(behavior Name …)
Shared vocabulary: a named set of ports, like an interface or a trait.
(implements Name)
A block, or a behavior, takes on a behavior’s ports.

Each form, with a toy

Blocks, :type and sketches

A block is any part of the system. :type grounds it in code, and its sketch says what it is for in one sentence. A block can hold levels of its own, so one picture works from the whole system down to a single file.

Click the triangle on Notes to close and open it. Select a block and choose Edit to change its type or sketch.

Levels

Levels run top to bottom, and each is named for the vocabulary it offers upward. A level’s sketch, when it has one, states the barrier: what the level above may know of it.

Point at “Rational numbers as numerators and denominators” to read its barrier. Click a level’s name to edit it.

Adjacency

Blocks in one level are independent. adjacent declares the exception, with a sentence that says why. Use it for two peers that are really one cooperation, and rarely.

Point at the line to read why. Drag Sync onto the line to join the group; select the line and press Delete to cut it.

Ports and messages

A message type is data. Inputs sit on a card’s top ear, outputs on its bottom ear. Keymap sends a KeyChord and Palette takes one, but neither names the other: something above wires them. Flow that goes upward, like an event or a callback, is always a message.

Click Keymap’s lower ear to open its outputs, then point at chord: Palette lights up, the block it can talk to.

refines and carries

Two relations between types, and only two. refines is is-a: a Click is an Event, so a port that takes events takes clicks. carries is has-a: a Snapshot holds a Selection and a Camera, drawn as dots on its lower ear. It never changes what a port takes.

Point at Camera: Snapshot, which carries it, lights up, and so does every block that touches either. Open History’s inputs and point at seen: every source of an Event, or of a subtype, lights up.

Behaviors and implements

A behavior is a promise many blocks make: a set of ports and a sketch of what holds. A block that implements it gains its ports.

Point at Surface: its implementers light up. Open Sidebar’s ears: the ports came from Surface.

Scope

Behaviors and message types are scoped: declared in a block, they are visible in it and in everything inside it. CardToken lives in Checkout, so only Checkout’s parts can use it. The viewer holds you to that while you edit.

Drag Form out of Checkout: every drop zone outside it is red. Drop it there anyway and it bounces back, with a toast that says why.

One language, any grain

A block maps to whatever you are working with. Change :type and keep the language: the same rules hold for files, packages and features.

What a message can be

If it crosses a boundary and neither side names the other, it is a message: an event, an HTTP request, a queue item, a callback, a CLI’s standard output, a database row. :type says which. carries says what is inside, so you can follow one value across all of them.

Point at Body: every message that holds a note’s text lights up, and so does every block that sends or takes one.

Inheritance, and how it is drawn

sbtel has two kinds of inheritance: data subtyping with refines, and shared vocabulary with behaviors.

Subtypes and port compatibility

An input takes its own type or any subtype of it, through any chain. Log takes every event, Menu every click, double clicks included, and Zoom only double clicks.

Open each listener’s top ear and point at its port to see which sources it accepts.

Behaviors as interfaces

Sidebar and Canvas implement Surface and get its ports; Canvas adds one of its own. A behavior’s card lists its implementers when you point at it.

Open Canvas’s top ear: frame comes from Surface, zoom is its own.

Extending, and parameters

A behavior may implement another, as a supertrait does, and may take parameters. Durable is a Store of Events. Cache K is a Store of K, so Thumbnails, a Cache of Image, has put and get typed Image.

Point at Store: every block that implements it, directly or through Durable or Cache, lights up.

Calling through an abstraction

Editor and DiskStore are peers, so Editor may not name DiskStore. It saves through Durable instead, and only Main, the composition root above them, builds the store and hands it over. That is dependency inversion, and sbtel check sees it: a binding to a behavior in scope passes under the rule abstraction.
